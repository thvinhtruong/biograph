````markdown
# BioGraph Enhancement & Integration Plan

## Overview

This document outlines the workflow and configuration for integrating
**BioGraph**—a local, Go-based CLI knowledge graph—into an academic study system
for the AI/ML Master's program at TU Darmstadt. The system uses spreading
activation retrieval, Hebbian learning, and exam-aware edge decay to optimize
study efficiency.

## 1. Directory Architecture

The workspace is structured to separate raw inputs, database state, and the
visual Obsidian vault.

```text
ai-ml-semester/
├── inbox/                  # Drop new lecture PDFs here (immutable sources)
├── biograph.yaml           # BioGraph configuration (LLM keys, max_hops, etc.)
├── biograph.db             # The SQLite graph store (nodes, edges, FTS5)
├── biograph.bleve          # BM25/TF-IDF index
└── vault/                  # The Obsidian-ready output (Read-Only)
    ├── entities/           # Subdirectories by category (algorithm, concept, theorem)
    ├── sources/            # Notes representing ingested PDFs
    └── dashboards/         # Dataview tracking dashboards
```
````

## 2. AI Assistant Context Protocol (`CLAUDE.md`)

To ensure AI coding assistants (like Cursor, Windsurf, or Claude) interact with
the knowledge base correctly, the repository must include a `CLAUDE.md` file.
Assistants are instructed **not** to parse the raw markdown files for complex
queries, but rather to use the `biograph` CLI.

**Core Directives for AI:**

- **Answering conceptual questions:** Use `biograph ask "<query>"` to tap into
  the hybrid router (Bleve -> LLM -> FTS5) and spreading activation engine.
- **Searching entities:** Use `biograph search "<entity>" --limit 5` for exact
  algorithms or theorems.
- **Graph Status:** Use `biograph status` to verify PDF ingestion success and
  graph shape.
- **Immutability:** Treat the `vault/` directory as read-only. Do not edit `.md`
  files or frontmatter directly. Let BioGraph's pipeline handle writes.

## 3. Obsidian Vault Visualization (Dataview Dashboard)

Since BioGraph handles weight updates internally via SQLite, Obsidian is used
purely as a visualizer. A Dataview dashboard (`vault/dashboards/exam_prep.md`)
tracks graph health and study priorities based on inbound/outbound links
generated by the CLI.

### Active Exam Radar

Tracks concepts tied to upcoming exams (decay factor frozen at 1.0).

```dataview
TABLE course AS "Course", exam_date AS "Exam Date", category AS "Type"
FROM "entities"
WHERE exam_date != null AND exam_date <= (date(today) + dur(30 days)) AND exam_date >= date(today)
SORT exam_date ASC
```

### Core Knowledge Hubs

Identifies intersection nodes (highest degree of connectivity), which attract
the most energy during spreading activation.

```dataview
TABLE category AS "Type", course AS "Course", length(file.inlinks) AS "Inbound Edges"
FROM "entities"
WHERE length(file.inlinks) > 0
SORT length(file.inlinks) DESC
LIMIT 10
```

### Orphaned Nodes

Identifies entities with no connections.

```dataview
TABLE category AS "Type", course AS "Course"
FROM "entities"
WHERE length(file.inlinks) = 0 AND length(file.outlinks) = 0
SORT last_updated DESC
```

## 4. The "Vibe-Coding" Study Loop

1. **Ingest:** Drop lecture PDFs in `inbox/` and run
   `biograph ingest inbox/<file>.pdf --course <course_name> --exam-date <date>`.
2. **Review:** Open the Obsidian Dataview dashboard.
3. **Activate:** Identify "Orphaned Nodes" and prompt the AI to run
   `biograph ask` comparing the orphaned node to a core hub.
4. **Reinforce:** The LLM answers, BioGraph's `ActivationEngine.Reinforce()`
   triggers, and new edges are forged in SQLite and written to the vault in
   real-time.
